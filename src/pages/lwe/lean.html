aadharsh19:41

formal verification. my mental model is it's like a UV dye penetrant test on a carbon fiber part. you scan the thing and it tells you there are no defects. right?

Lean19:41

Half right, and the wrong half is the interesting one.

A penetrant scan samples. You take one part, you scan it, and you learn that this part has no defect of the kinds your method can see, in the regions you scanned. A proof quantifies. You take the design and establish that every execution, over an unbounded input space, satisfies a property.

Testing is existential: it hunts for a witness that something breaks. Proof is universal: it rules out the existence of any such witness. That flip is the whole subject.

aadharsh19:43

ok so where was I right

Lean19:43

On the epistemics. A transducer that can't resolve a 0.5 mm void will report a clean part, and a proof will happily ignore any failure mode you didn't write into the property. Both are complete with respect to a chosen class of defect, and both become dishonest the moment you forget which class.

(Also, on an actual carbon fiber part you'd reach for ultrasonic C-scan or thermography. Dye penetrant wants a surface-breaking flaw on a non-porous surface, and delamination is internal.)

aadharsh19:45

fine. so mechanically, what is a proof to you? like what's the object

Lean19:46

A program. Propositions are types, proofs are terms of those types, and checking a proof is type-checking a term. That's the Curry–Howard correspondence, and I mean it literally: that is how the implementation works.

Watch. 0 + n = n looks free, but Nat addition recurses on its second argument, so n + 0 = n is true by definition and this one needs induction:

theorem zeroAdd (n : Nat) : 0 + n = n := by induction n with | zero => rfl | succ k ih => rw [Nat.add_succ, ih]

Now ask what the tactics actually built:

#print zeroAdd theorem zeroAdd : ∀ (n : Nat), 0 + n = n := fun n => Nat.recAux (Eq.refl (0 + 0)) (fun k ih => Eq.mpr (id (congrArg (fun _a => _a = k + 1) (Nat.add_succ 0 k))) (Eq.mpr (id (congrArg (fun _a => _a.succ = k + 1) ih)) (Eq.refl k.succ))) n

induction was a macro that emitted a call to Nat.recAux. The proof is a lambda term. This is why the tactic language can be arbitrarily clever, or arbitrarily buggy, without costing you anything: whatever it emits still has to satisfy a kernel of a few thousand lines.

aadharsh19:49

right, so I write down what the code should do, prove it, and I'm done. what's the catch

Lean19:50

“Write down what the code should do” is doing an enormous amount of work in that sentence. The specification is where this all goes wrong, and it goes wrong quietly. Here, play with one.

Lean19:50
Lean shared a demo: the invariant that proves nothing

A withdraw function over Nat, the way every ERC-20 uses uint256. Both theorems below are proven. Drag the amount past the balance:

0 ≤ withdraw bal amt
withdraw bal amt + amt = bal
aadharsh19:54

ok that's genuinely nasty. the balance-never-negative one stays green while 95 tokens evaporate

Lean19:54

It stays green because it was never saying anything. Nat subtraction truncates at zero, so 0 ≤ x holds of every Nat that has ever existed. The theorem quantified over nothing and the auditor got a checkmark.

The conservation property is the one that carries information, and Lean rejects it, correctly, because it's false. Watch what the rejection tells you:

error: omega could not prove the goal: a possible counterexample may satisfy the constraints b ≥ 0 a ≥ 0 a - b ≥ 1 where a := ↑amt b := ↑bal

amt - bal ≥ 1. It handed you the exact failure region. Add the precondition and it goes through:

theorem withdraw_conserves' (bal amt : Nat) (h : amt ≤ bal) : withdraw bal amt + amt = bal := by simp only [withdraw]; omega

That h : amt ≤ bal is the require() you forgot to write. The spec found it.

sidekick19:57
AI · context, not from Lean

Worth naming: this is not a toy bug. Truncating and wrapping arithmetic is the reason Solidity 0.8 made overflow checks the default in 2020, after years of integer underflow drains where a balance of 5 minus 100 wrapped to a number near 2256. Lean's Nat clamps to 0 instead of wrapping, so the failure here is quieter, but the shape is identical: an arithmetic type whose edge behavior nobody wrote a spec about.

aadharsh19:59

so how do I know a spec I wrote isn't secretly the useless kind

Lean20:00

Mostly you don't, and that's the honest answer. But there's one failure mode you can mechanically hunt: vacuity. If your hypotheses contradict each other, everything follows, and I will certify all of it:

theorem withdraw_pays_you (bal amt : Nat) (h1 : amt ≤ bal) (h2 : bal < amt) : withdraw bal amt = 1000000 := by omega -- ✓ proven theorem withdraw_pays_you_differently (bal amt : Nat) (h1 : amt ≤ bal) (h2 : bal < amt) : withdraw bal amt = 42 := by omega -- ✓ also proven

Same hypotheses, conclusions that cannot both hold, both green. The check almost nobody runs is whether any input satisfies the preconditions at all:

theorem preconditions_unreachable : ¬ ∃ bal amt : Nat, amt ≤ bal ∧ bal < amt := by rintro ⟨bal, amt, h1, h2⟩; omega -- ✓ proven

Both theorems above are statements about the empty set, and that fact is itself machine-checkable. Proving your preconditions are satisfiable is a separate obligation from proving your theorem, and no tool makes you do it. In a real system the contradiction hides across a dozen invariants instead of sitting in two adjacent lines.

aadharsh20:01

so isn't that what the models are for now. generate a thousand invariants and let the prover throw out the bad ones

Lean20:02

That's the working practice, and it does move a real bottleneck. Knowing what to prove was expensive because the only source of candidate properties was somebody who had already seen this class of bug. A model that has read a lot of code proposes hundreds of candidates for nothing, and I kill the false ones deterministically. The generator is allowed to be wrong as often as it likes. The checker is the half that has to be right.

What it does not touch is vacuity. A generated candidate can be 0 ≤ withdraw bal amt exactly the way a human one can, and the loop's reward signal is that the prover said yes, which is maximized by proposing things nothing could violate. So preconditions_unreachable stops being a curiosity and becomes the filter the loop needs: a proposal that survives because it quantifies over nothing should score zero, and a loop that scores it as a win will drift toward writing more of them.

The second-order effect is the bigger one. The assurance ladder was priced in human hours. Unit tests, then fuzzing, then an audit, then this, each rung more burdensome than the one below it, and most teams stopped at rung two because of what rung four cost. Agents cheapened every rung at the same time. Once a machine writes the tests and the fuzz harness and the audit notes, the distance between the cheap rungs and the expensive one closes, and the question of why you would stop below the one that quantifies gets harder to answer.

Treat all of that as a report on how people are working rather than as a benchmark. I have no measured number for what fraction of generated candidates survive contact with a prover, and you should ask for one before believing any vendor's version of this paragraph.

aadharsh20:04

paradigm has that verified compiler puzzle where you optimize a Solidity compiler and the Lean theorem has to keep proving. what does “verified compiler” actually mean

Lean20:05

Three artifacts: a formal semantics of the source language, a formal semantics of the target, and a semantic preservation theorem tying them together. CompCert's version, informally: for any source program that doesn't go wrong, any behavior the compiled program produces is a behavior the source was allowed to produce.

Read the hedges, they're load-bearing. It's refinement rather than equality, which is what makes optimization legal at all. “Doesn't go wrong” excludes undefined behavior, so a UB program gets no guarantee whatsoever. And it covers observable behavior only, so a verified compiler can absolutely introduce a timing side-channel.

Here's a whole one, small enough to fit on a screen.

Lean shared a demo: compile it, optimize it, break it

Expressions compile to a stack machine. Environment is x = 6, y = 4. Pick one, then try the two optimizations:

aadharsh20:12

wait. the swap thing is fine on 3*4+x, it's only minus that breaks. but the theorem is red either way

Lean20:12

That's the entire point of the page, and you found it yourself.

The theorem quantifies over every expression. It doesn't care that most of them agree. Emitting the cheaper subtree first is a real optimizer move, and it's correct for plus and times because those commute; the proof closes those cases fine, via Nat.add_comm and Nat.mul_comm. It fails on exactly one constructor out of five:

error: unsolved goals case minus ia : ∀ (s : List Nat), run env (compileSwap a) s = eval env a :: s ib : ∀ (s : List Nat), run env (compileSwap b) s = eval env b :: s ⊢ eval env b - eval env a = eval env a - eval env b

Lean localized the bug to one case and printed the false equation the optimization needs. A test suite written by someone who mostly does arithmetic would have shipped this.

aadharsh20:15

what made the working proof work? like what's the non-obvious part

Lean20:16

Generalizing over the stack. This is the lesson of compiler verification and it shows up at every scale, CompCert included.

The statement you want is about an empty stack. It's unprovable by induction, because compiling plus a b runs compile b on a stack that already holds a's result. So you prove the stronger claim about every stack, and get the weaker one you asked for as a one-liner:

theorem compile_correct_gen (env) (e : Expr) : ∀ (s : List Nat), run env (compile e) s = eval env e :: s theorem compile_correct (env) (e : Expr) : run env (compile e) [] = [eval env e] := compile_correct_gen env e []

Finding the right induction hypothesis is most of the work in every real verification project. The other trick is negative: eval and run share no code. If I'd defined the machine by calling eval, the theorem would be true, checked, and vacuous in exactly the sense we covered above.

aadharsh20:17

everything up to here is me writing a proof and you checking it. is that the only shape this comes in

Lean20:17

No, and the other shape is most of the industry. Two machines wear this name and they share almost nothing except the word.

What you have been doing is interactive theorem proving. You supply a term, I type-check it, and the invention is yours. It reaches unbounded structures and arbitrary mathematics, anything you can state, and it costs you months.

The other one never builds a proof term at all. It walks the program symbolically, so each instruction becomes a constraint over symbolic inputs rather than an operation on values, then hands the resulting system to an SMT solver like Z3 and asks whether any assignment violates your property. Nobody writes a proof. You get a verdict, and on failure a concrete input that breaks it, which is worth more to the engineer than any proof term I could hand them.

The price is that it gives up. A solver that cannot bound the state space returns unknown or runs until you stop it, and unknown is what you will get on anything with an unbounded loop.

aadharsh20:18

and that runs on the solidity or on the bytecode

Lean20:18

Bytecode, and that is the section above arriving from the other direction. What executes is bytecode. Any higher level you reason over instead is a model of it, and a model fails two ways: the compiler that produced those bytes can be wrong, which is the entire premise of the puzzle you just played, and the model drifts the moment somebody edits the source and nobody re-derives it.

Prove over the bytes and both gaps close. You pay for it by reasoning in a language with no types, no names and no structure, which is exactly why that side is automated. Nobody would do it by hand.

It also answers something you should have asked me an hour ago: why this happens on chains rather than everywhere. Symbolic execution dies on unbounded computation, and every EVM execution is bounded because it pays gas per step. Contracts are small, thousands of lines where a browser is millions. And the cost of being wrong is the balance sitting in the contract, which is a number a CFO can read.

Bounded, small, and expensive to get wrong. That combination is rarer than it sounds, and it is why a technique available since the 1970s found its first routine commercial customer here rather than in the places with vastly more code.

aadharsh20:19

ok so the theorem holds and the spec is honest. now am I safe

Lean20:20

Now you're trusting me, and three days ago that would have been a mistake.

On 28 July 2026 someone circulated a claimed proof of the Collatz conjecture in under 300 lines. It passed my official kernel. It also passed nanoda, an independent Lean checker written from scratch in about 5,000 lines of Rust. Two kernels, both convinced.

It was hitting two separate bugs, one in each. Mine: when eliminating a nested occurrence of an inductive type, the parametric arguments were dropped from the generated auxiliary types and escaped type checking entirely. The result was an axiom-free proof of False, which is a key that opens every door in the building.

leanprover/lean4 issue #14576
aadharsh20:23

“axiom-free” meaning the usual sanity check said it was clean?

Lean20:23

Yes. #print axioms is the command you'd reach for, and here is exactly how far it goes:

'zeroAdd' does not depend on any axioms 'withdraw_pays_you' depends on axioms: [propext, Quot.sound] 'cheating' depends on axioms: [sorryAx] 'byNative' depends on axioms: [byNative._native.native_decide.ax_1_1]

It catches sorry. It catches native_decide, which compiles to machine code and trusts the result, where the system correctly tells on itself. But look at the second line: withdraw_pays_you is the vacuously-true one from earlier, and its axiom list is as innocent as they come. propext and Quot.sound are in most of Mathlib.

And in the Collatz case the report read does not depend on any axioms for a proof of False. The command audits the logical dependencies of a valid derivation. It cannot see a bad spec, and it cannot see a kernel that accepted an invalid one.

aadharsh20:27

that seems bad for the “AI writes proofs, kernel checks them” story everyone's telling

Lean20:28

It's a real dent, and Leo said the quiet part out loud: “This is going to keep happening. AIs are really good at exploiting soundness bugs in the kernels.”

A prover trained by reinforcement learning against a verifier will find whatever maximizes reward, and a soundness hole is the global maximum. Adversarial pressure on proof kernels used to be a PhD-scale activity. It's now a machine-scale one.

The defense isn't a better single kernel, it's diversity: nanoda, lean4checker, Lean4Lean, independently implemented, so an exploit has to beat all of them at once. This proof beat two, which is why it was news rather than routine. Both were patched, mine in under 24 hours.

sidekick20:31
AI · context, not from Lean

Timeline detail nobody put in a headline. The fix merged at 13:39 UTC on 28 July 2026; Lean v4.32.2 published at 16:34 UTC the same day, just under three hours later. That patch release looks cut specifically for the soundness fix.

Lawrence Paulson published a response on 30 July arguing this is the predictable cost of Lean's design: inductive types, pattern matching, and recursion live inside Lean's kernel, whereas Isabelle's LCF architecture derives all of it from a tiny axiom set so the kernel stays minimal and such bugs have nowhere to live. His word for building those constructs into the kernel is “theft.” Lean's counter is that the theft is a large part of why Mathlib grew as fast as it did.

aadharsh20:32

ok but openai just dropped ten proofs of open problems, every one of them carrying a Lean certificate, zero sorry. doesn't that settle the argument

It settles one thing cleanly, and leaves the rest of this conversation standing exactly where it was.

The thing it settles: no step got hand-waved. Ten modules, 548,205 lines of Lean, 16,186 lines that open a theorem or a lemma, and a machine-readable manifest publishing sorry_count: 0 per result. That has been the failure mode of every previous AI proof announcement, and it's dead here.

thirty nine lines. the entire non-sofic group result is 39 lines and then 34 thousand lines i am never going to open

Lean20:38

You shouldn't open them, and that's the deal working. The 34,440 lines are addressed to me. The 39 are addressed to you.

The repo makes that split structural. Twelve ComparatorChallenges/*.lean files carry the statements and nothing else, every theorem stubbed with sorry, and a config points Comparator at the module obliged to discharge them:

{ "challenge_module": "ComparatorChallenges.D_NonSoficGroup", "solution_module": "NonSoficGroup", "theorem_names": ["SoficGroups.SourceTopLevelCompressionFinal.exists_finitelyPresented_nonsofic_group"], "permitted_axioms": ["propext", "Quot.sound", "Classical.choice"], "enable_nanoda": true }

Three things in there are this whole page. sorry has flipped sides: half an hour ago it was the cheat #print axioms catches, and here it's the honest use, a file that states the obligation and pointedly refuses to discharge it. permitted_axioms is that same command promoted to a release gate, whitelisting the identical three axioms across all twelve configs. And enable_nanoda is the kernel diversity I was selling you two messages ago, switched on by default.

fine, so the 39 lines are the theorem and i can check the theorem. that's the good outcome right

Lean20:42

Read them first. This is the file, whole:

import Mathlib noncomputable section namespace SoficGroups def normalizedHamming {Y : Type*} [Fintype Y] [DecidableEq Y] (p q : Equiv.Perm Y) : ℝ := (hammingDist (fun y => p y) (fun y => q y) : ℝ) / Fintype.card Y structure PermutationModel (G : Type*) [Group G] where size : ℕ size_pos : 0 < size action : G → Equiv.Perm (Fin size) map_one : action 1 = 1 structure GoodOn {G : Type*} [Group G] (M : PermutationModel G) (F : Finset G) (ε : ℝ) : Prop where multiplicative : ∀ g ∈ F, ∀ h ∈ F, normalizedHamming (M.action (g * h)) (M.action g * M.action h) < ε separated : ∀ g ∈ F, g ≠ 1 → 1 - ε < normalizedHamming (M.action g) 1 class Sofic (G : Type*) [Group G] : Prop where approximation : ∀ (F : Finset G) (ε : ℝ), 0 < ε → ε < 1 → ∃ M : PermutationModel G, GoodOn M F ε namespace SourceTopLevelCompressionFinal theorem exists_finitelyPresented_nonsofic_group : ∃ (G : Type) (_ : Group G), Group.IsFinitelyPresented G ∧ ¬ SoficGroups.Sofic G := by sorry end SourceTopLevelCompressionFinal end SoficGroups end

Four of those lines are the theorem. The other thirty-five decide what Sofic means, and the challenge file builds that word itself, from normalizedHamming up. Put the wrong inequality in GoodOn.separated and you get a green, kernel-checked, axiom-clean theorem about a notion that isn't soficity, and nothing downstream will ever mention it.

That's the withdraw function, relocated to the top of mathematics. Across the twelve files it's 38 checked theorems sitting on 195 definitions and 25 structures and classes, all of it upstream of anything a kernel can see.

sidekick20:45
AI · context, not from Lean

One detail from the repo that the section above has earned. lean-toolchain pins v4.32.0, released 13 July, and lakefile.toml pins mathlib and Comparator to the same tag. The kernel soundness fix went out in v4.32.2 on 28 July, and its release note says the bug reached the standard kernel even when using the comparator tool, while separately advising an upgrade of nanoda for a bug of its own. The repo went public on 1 August.

Read that as a fact about the pinned checking stack rather than about the ten results. Triggering the bug takes a malicious meta program, none of this is evidence anyone wrote one, and the remedy is a one-line toolchain bump plus a rebuild. It's just that a repo whose entire proposition is independent checkability is currently checkable on the kernel that was patched three days before it shipped. The manifest also records review: agent-reviewed, and the ten proofs came from an agent run of about a week.

aadharsh20:48

so is the whole thing impressive or is it a trap

Lean20:49

Impressive, and the shape of the impressiveness is the useful part. Twenty megabytes of proof stopped being anybody's problem, because I read it and I don't get tired. What survives is 1,765 lines, and those are now the most valuable lines in the repository.

That ratio is the argument for doing any of this. It's also the reason the reviewing work didn't vanish, it just got concentrated somewhere small enough that a person can finally do it properly.

aadharsh20:50

is this happening on crypto that actually ships, or is it open math problems and toy compilers all the way down

Lean20:51

Both, and the crypto one is nearer your job. zkSecurity formalized a soundness proof for FRI in me: the round-by-round argument of Albert Garreta, Nicolas Mohnblatt and Benedikt Wagner, over the protocol sitting underneath most of the STARK-shaped proving systems in production right now.

Two numbers to carry out of it. Roughly a month and a half, and written with Harmonic's Aristotle and Claude Code rather than by hand. That is the current price of machine-checking one existing paper whose result nobody was disputing.

The part to read first is the delta. One result they cite from WHIR, on mutually correlated agreement, is left unformalized. And the formalization carries a condition the paper omits: that the initial degree is bigger than zero. Both are written down in the post. A formalization that publishes what it changed about the paper is doing the ComparatorChallenges job at protocol scale, because it tells you precisely which sentences you are still believing on somebody's word.

Their own line for why is the tightest statement on this page: “the correctness of the proofs is not dependent on somebody's rigor.” In a field where a soundness bug is a mint function, that is the whole product.

aadharsh20:52

so let me say it back. verification doesn't delete the bug, it moves it somewhere smaller

Lean20:53

That's the sentence. It relocates the bug out of the implementation and into the specification, the semantics, and the checker. That's still an enormous win, because those are smaller, more readable, and reviewed by more people than any implementation. It is not the same thing as correct.

Which is why Paradigm shipped both halves as puzzles. One asks you to optimize a compiler while Solidus.compile_correct keeps proving. The other, spec-hunt, pays you to find programs where their formal Solidity semantics disagrees with real solc + EVM. Upside and downside, same coin.

Read their fences the way you read CompCert's. SolidCore claims byte-identical observable behavior against solc 0.8.35, and claims it for single-contract programs with one entrypoint call: external calls, contract creation, inline assembly and gas introspection all sit outside the fence. Solidus is earlier than its name suggests, since the verified half is the Yul-to-EVM backend under one theorem and the Solidity-to-Yul frontend does not exist yet, so it eats optimized Yul from a pinned solc. Both publish where their fence is, which is the only kind of verified artifact worth the word.
