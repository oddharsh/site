scheduler.yield() / main-thread responsiveness Chrome 129 · FF 142 · no Safari

WebKit: unstated A promise you await in the middle of a long task: it hands the main thread back to the browser to service pending input/paint, then resumes your loop, and crucially resumes at the front of the queue, not the back like setTimeout(0). So you stay responsive without losing your turn to unrelated work. It's shipped in Chrome and Firefox 142 (no flag), so the demo below is live: the concept, then a real measured run, then the code.

Click a button and watch the dot. The single 600 ms task freezes it; the chunked version yields every ~20 ms so it keeps gliding, same total work, responsive throughout.

// today on the site: cold-KV tracklist fallback builds ~50 rows
// in one go, blocking input on a slow phone.
for (const t of tracks) renderTrackRow(t);   // one long task

// with scheduler.yield(), guarded so it ships everywhere:
const yieldNow = (window.scheduler && scheduler.yield)
  ? () => scheduler.yield()
  : () => new Promise(r => setTimeout(r, 0));  // fallback

let i = 0;
for (const t of tracks) {
  renderTrackRow(t);
  if (++i % 8 === 0) await yieldNow();   // breathe every 8 rows,
}                                        // resume at front of queue

On the site: the offender is the client-side Spotify tracklist fallback (the cold-KV path that renders full-fidelity rows: artist links, cover art, tooltip wiring). Today that's one synchronous burst. scheduler.yield() would let it chunk while keeping taps and scroll alive, without the back-of-queue penalty of a setTimeout(0) shim. It graduates to the homepage trivially because it's a guarded enhancement (typeof check, same-shape fallback), so Safari and Firefox just take the plain loop.

Your browser doesn't expose scheduler.yield(), the live demo below still runs and stays responsive, it just takes the setTimeout(0) fallback path instead. To get the real primitive: Chrome 129+, shipped, no flag.

        The QUERY method RFC 10008
        Published Jun 2026 · every engine sends it · no cache stores it
      

      

        HTTP has had a hole in it since the beginning: a request that is safe
        and idempotent like GET, carrying a body like
        POST. QUERY fills it. The query lives in the
        request content, the method is declared safe and idempotent, so an
        intermediary may retry it after a timeout and a cache may store the
        response. Servers picked it up quickly, and a resource advertises which
        body formats it takes through a new Accept-Query response
        header. The headline everywhere is "a GET with a body", and
        the interesting part of this one is the layer underneath, because a
        cache that stores a QUERY response has to key on the
        request body, and almost nothing does yet.
      


      

        

          Measured against this origin on 2026-08-12, since the support tables
          describe engines and the thing that decides whether you can use it is
          the CDN in front of you:

          In the browser half, new Request(url, {method:'QUERY', body})
          throws in no engine and the request goes out on the wire, because
          fetch forbids a body only on GET and
          HEAD, and blocklists only CONNECT,
          TRACE and TRACK. What browsers are still
          missing is the storing half: the HTTP cache holds
          GET responses, and cross-origin
          QUERY needs a preflight because it is not
          CORS-safelisted.
        

      


      

        On the site: /mcp is the one surface where this would ever
        land, and the classification work is already done. Every tool in
        lib/mcp-tools.js carries readOnlyHint and
        idempotentHint, and the two that write to D1
        (representation_capture, representation_compare)
        declare readOnlyHint: false beside the INSERT. That pair of
        annotations is exactly the eligibility test for QUERY.
        Sharper tell: the server already emits ttlMs and
        cacheScope on list and read results, which exist because a
        POST transport cannot be cached, so the protocol rebuilt caching one
        layer up. QUERY would hand that job back to HTTP, and the
        change would live once in lib/mcp-protocol.js where both
        servers on this origin would inherit it.
      

      

        The reason it stays a forward-look rather than a migration: everything
        cacheable here is keyed by URL. Workers Cache, caches.default,
        the edge, and both compression-dictionary tiers all key on the URL, and
        the per-page dictionary offers match by URLPattern. A
        QUERY response has no URL to key on, and the varying part
        sits in a body where no Vary header reaches. This page's
        own routes lean the other way on purpose too: /terminal
        keeps its state in query parameters so a frame can be forked,
        bookmarked and replayed, and /lens takes
        ?url=. Adopting QUERY would trade that away.
        The signal worth waiting for is the MCP specification adopting it,
        because no client will send one before then.
      

      

        The chip below reads no for every visitor, and it is hardcoded. A
        round-trip probe (construct a QUERY Request,
        read the method back) returns true in every engine, since
        fetch never validates a method name past its blocklist.
        That is the same trap as sizes=auto further up. The
        capability that actually matters, whether any cache along the path
        stores the response, is not observable from a page at all.

        and Chromium, WebKit and Gecko have all now agreed to take it out. Chromium has
        the deprecation staged across 2026.
      

      

        What makes it worth a card rather than a footnote is the migration story, which
        is unusually honest for a removal: the replacement is a
        WebAssembly build of libxslt,
        so the code doesn't disappear, it moves out of the browser's trusted
        computing base and into the page's own sandbox. The platform loses an
        attack surface, sites that need it keep working, and it costs a download.
      

      

        On the site: no XSLT anywhere, so the removal costs nothing here directly, and
        the reason to write it down is a rule this page keeps re-learning. Old and widely
        deployed is not the same as safe to depend on. The retired service worker, the
        THUMB_VERSION query-string cache-buster and the View Transitions
        that shipped for most of 2026 were each removed for a version of the same
        argument, and each one felt permanent while it was in.
      

      
No XSLTProcessor in this browser, so the removal has already reached you.

    


    

    
    

      
The long tail: independent engines

      

        "The platform" isn't only Chromium, Gecko, and WebKit. Two
        teams are building new engines largely from scratch, a useful reminder
        that the frontier above is the front, while most of the web runs
        well behind it. Both are pre-release and racing toward baseline
        rather than 2026 CSS, so on the features on this page they're mostly
        "not yet." Status as of mid-2026: check the live links, this moves fast.
      


      

        
Ladybird pre-alpha

        

          A from-scratch engine (LibWeb) with no Chromium/WebKit/Gecko code,
          built by a nonprofit. It's now on the WPT dashboard (~2.07M
          subtests passing) and racing to render the real web.
        

        

          On these features: it has the Popover API, and added
          initial CSS anchor positioning (position-anchor)
          in April 2026. The newer/niche ones (text-box-trim,
          contrast-color, scroll-driven animations, corner-shape, masonry)
          aren't there yet. Baseline first, frontier later.
        

        

          Live: ladybird.org/news
          · wpt.fyi (ladybird)
        

      


      

        
Servo alpha ~Jul 2026

        

          A Rust engine, originally Mozilla's, now under the Linux
          Foundation and aimed at embedding. WPT pass rate around 95% in its
          focus areas; a desktop browser is still years out.
        

        

          It spends its energy on layout fundamentals (flexbox, grid, tables,
          floats), with recent adds like cursor color and
          content: image(). It generally hasn't implemented the
          frontier CSS here yet (popover, anchor positioning, text-box-trim).
        

        

          Live: servo.org/blog
          · github.com/servo
        

      


      

        The point: these two are why "ship to baseline, prototype
        the frontier" is the right discipline. To support the independent,
        indie-web engines, I lean on what's broadly shipped and leave
        what's newest in one browser parked here. Good deep-dive comparison:
        Browser Engines 2026.
